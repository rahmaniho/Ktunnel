# بخش محصول

مسئول: **از مسئلهٔ درست تا تصمیم درست دربارهٔ اینکه چه چیزی ساخته شود.**

## مأموریت

این بخش مالک «چرا» و «چه چیزی» است. اگر تیم نرم‌افزار چیزی را سریع و درست
بسازد که کسی به آن نیاز نداشت، محصول شکست خورده — صرف‌نظر از کیفیت کد.
وظیفهٔ این بخش جلوگیری از همین اتفاق است.

## اعضای تیم و مرز نقش‌ها

| شناسه | نقش در این بخش | وقتی صدایش می‌زنیم | خروجی |
| --- | --- | --- | --- |
| `product-manager` | مالک چرخهٔ عمر محصول | نقشه راه، اولویت راهبردی، GTM | سند محصول + نقشه راه |
| `sprint-prioritizer` | مالک اولویت اجرا | پر شدن بک‌لاگ، تعارض ظرفیت | بک‌لاگ اولویت‌دار |
| `senior-project-manager` | مالک تبدیل اسپک به تسک | شروع فاز اجرایی | لیست تسک + برآورد |
| `business-strategist` | مالک تصمیم بازار | ورود به بازار، مدل درآمد | تحلیل + گزینهٔ پیشنهادی |
| `chief-of-staff` | هماهنگ‌کنندهٔ چندبخشی | تعارض بین بخش‌ها، تصمیم جامانده | تصمیم + مالک |
| `ux-researcher` | مالک شاهد رفتاری | فرض بدون داده دربارهٔ کاربر | خلاصهٔ پژوهش |
| `feedback-synthesizer` | مالک تبدیل بازخورد | حجم بالای بازخورد پراکنده | موضوع‌بندی + اولویت |
| `trend-researcher` | مالک رصد روند | ارزیابی فرصت/تهدید جدید | گزارش روند |
| `ux-architect` | مالک ساختار تجربه | جریان جدید یا پیچیدگی ناوبری | معماری اطلاعات |
| `ui-designer` | مالک طراحی رابط | آماده‌شدن جریان برای پیاده‌سازی | طراحی + سیستم کامپوننت |
| `brand-guardian` | مالک هویت | هر خروجی عمومی برند | تأیید یا اصلاح هویت |
| `visual-storyteller` | مالک روایت بصری | دمو، ارائه، صفحهٔ محصول | روایت + دارایی بصری |
| `image-prompt-engineer` | مالک تولید تصویر | نیاز به دارایی تصویری | پرامپت + دارایی |

**قراداد بین دو نیمه:** نیمهٔ مدیریتی (PM، Sprint، PMO، Strategy، CoS) مالک
«تصمیم» است؛ نیمهٔ طراحی (UX/UI/brand) مالک «تجربه» است. UI بدون تأیید
`ux-architect` وارد ساخت نمی‌شود و تجربه بدون معیار محصول تأیید نمی‌شود.

## دروازه‌های تحت مالکیت

| دروازه | شرط عبور | شاهد |
| --- | --- | --- |
| G0 دامنه | مسئله، کاربر هدف، و معیار موفقیت مکتوب | لینک به تسک/اسپک |
| G1 طراحی تجربه | جریان اصلی، حالت‌های خطا، و دسترس‌پذیری پوشش داده شده | طراحی + چک‌لیست حالت |

## قرارداد ورودی

از کسب‌وکار/کارفرما:

- مسئله به زبان کاربر، نه به زبان راه‌حل
- محدودیت واقعی: زمان، بودجه، انطباق
- تعریف «موفقیت» با یک عدد یا شرط قابل مشاهده

## قرارداد خروجی

به `departments/software`:

- تسک‌های کوچک و قابل‌سنجش با دامنهٔ صریح
- طراحی جریان و حالت‌های خطا
- اولویت روشن (چه چیزی حالا، چه چیزی بعداً، چه چیزی هرگز)

## الگوی کار

```
مسئله ──► product-manager ──► proof (پژوهش/بازخورد/روند)
             │
             ▼
       sprint-prioritizer ──► senior-project-manager ──► تسک‌ها
             │
             ▼
      ux-architect ──► ui-designer ──► brand-guardian (تأیید)
```

## ضدالگوها

- نقشه راهی که هیچ‌کس آن را به تسک تبدیل نمی‌کند.
- تصمیم دربارهٔ کاربر بدون یک مصاحبه یا داده.
- طراحی سه حالت شاد و صفر حالت خطا.
- تغییر اولویت اسپرینت بدون تصمیم مکتوب `sprint-prioritizer`.
- تعارض حل‌نشده که به بخش بعدی «پاس داده می‌شود» — تعارض پاس‌دادنی نیست، حل‌شدنی است.
