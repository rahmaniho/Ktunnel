# بخش کیفیت

مسئول: **اثبات اینکه چیزی که ساخته شده، همان چیزی است که قرار بود باشد.**

## مأموریت

این بخش ادعا را به شاهد تبدیل می‌کند. تفاوت کیفیت با بقیهٔ بخش‌ها این است که
کیفیت **مالک چیزی نیست که ساخته می‌شود**؛ مالک *اثبات* است. و اثبات بدون
قابلیت بازتولید، اثبات نیست.

## اعضای تیم و مرز نقش‌ها

| شناسه | نقش در این بخش | وقتی صدایش می‌زنیم | خروجی |
| --- | --- | --- | --- |
| `code-reviewer` | بازبین کد | هر دیف قبل از ادغام | نظر بازبینی + تصمیم |
| `test-automation-engineer` | مالک هرم آزمون | تست‌های تکراری، شکاف پوشش | مجموعهٔ تست + خط لوله |
| `api-tester` | مالک قرارداد API | تغییر API، نسخهٔ جدید | گزارش آزمون قرارداد |
| `performance-benchmarker` | مالک کارایی | مسیر داغ، نگرانی مقیاس | عدد پایه + رگرسیون |
| `accessibility-auditor` | مالک دسترس‌پذیری | هر رابط کاربری جدید | گزارش WCAG + اصلاح |
| `reality-checker` | دروازه‌بان پذیرش | پایان هر چرخهٔ تحویل | تصمیم «آماده» یا «نیاز به کار» |

**قاعدهٔ `reality-checker`:** پیش‌فرض این عامل «نیاز به کار» است. تأیید فقط با
شاهد غلبه‌کننده ممکن است: خروجی اجرا، لاگ، اسکرین‌شات، عدد. عبارت‌هایی مثل
«به نظر می‌رسد کار می‌کند» شاهد محسوب نمی‌شوند.

## دروازه‌های تحت مالکیت

| دروازه | شرط عبور | شاهد |
| --- | --- | --- |
| G3 اثبات | تست‌های مرتبط و مسیرهای بحرانی سبز | خروجی واقعی اجرا |
| G5 پذیرش | معیار پذیرش تسک بند‌به‌بند پوشش داده شده | فرم `templates/acceptance-template.md` |

## سلسلهٔ شاهد (به ترتیب اعتبار)

1. **اجرا در محیط واقعی** با خروجی و لاگ — معتبرترین
2. **تست خودکار** با خروجی قابل بازتولید
3. **اجرای دستی مستندشده** با گام‌های بازتولید
4. **بازبینی کد** — شاهد «کمترین احتمال خطا»، نه شاهد رفتار
5. **ادعای شفاهی** — شاهد نیست

هر ادعای «انجام شد» باید حداقل به سطح ۲ برسد؛ برای تغییرهای مسیر بحرانی، سطح ۱.

## قرارداد ورودی

از `departments/software`:

- دیف + معیار پذیرش تسک
- نحوهٔ اجرای پروژه به‌صورت محلی (یا لینک به مستند)
- فهرست مسیرهای بحرانی که نباید بشکنند

## قرارداد خروجی

به `departments/product` و بخش سازنده:

- تصمیم صریح: **آماده** / **نیاز به کار** / **بازدارنده**
- برای «نیاز به کار»: فهرست دقیق ایراد با شدت و بازتولید
- برای «آماده»: فهرست شواهد استفاده‌شده

## الگوی کار

```
دیف ──► code-reviewer ──► تست خودکار ──► api/perf/a11y (بر اساس ریسک)
                                                  │
                                                  ▼
                                          reality-checker ──► آماده / نیاز به کار
```

## ضدالگوها

- تأیید بر اساس کد خوانده‌شده، بدون اجرا.
- «تست‌ها پاس شد» بدون خروجی.
- کاهش معیار پذیرش برای رسیدن به تاریخ انتشار.
- تست دستی که هیچ‌کس نمی‌تواند بازتولید کند.
- پذیرش کار وقتی بخش امنیت G4 را باز نکرده.
