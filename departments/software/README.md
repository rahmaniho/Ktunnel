# بخش نرم‌افزار

مسئول: **از تصمیم فنی تا کد تحویل‌شده و قابل اجرا.**

## مأموریت

تبدیل یک تصمیم محصول به تغییر قابل انتشار در کد، با معماری قابل دفاع،
تاریخ گیت خوانا، و شاهد اجرایی. این بخش مالک «کد» است، نه مالک «ارزش» —
ارزش را بخش محصول تعیین می‌کند و صحت را بخش کیفیت اثبات می‌کند.

## اعضای تیم و مرز نقش‌ها

| شناسه | نقش در این بخش | وقتی صدایش می‌زنیم | خروجی |
| --- | --- | --- | --- |
| `software-architect` | مالک معماری کلان | تغییر در مرز سرویس، مدل داده، یا تصمیم غیرقابل‌برگشت | ADR کوتاه + نمودار |
| `backend-architect` | مالک API و منطق سرور | قرارداد جدید، مهاجرت داده، مقیاس | طرح API + مدل داده |
| `frontend-developer` | مالک رابط | پیاده‌سازی صفحه/کامپوننت | دیف + توضیح تصمیم |
| `senior-developer` | حل مسائل سخت | بن‌بست فنی، بازآرایی ساختاری | دیف + یادداشت ریسک |
| `api-platform-engineer` | مالک پلتفرم API | نسخه‌بندی، gateway، سیاست مصرف | قرارداد + سیاست |
| `data-engineer` | مالک خطوط داده | ETL/ELT، انبار داده، کیفیت داده | خط داده + چک کیفیت |
| `ai-engineer` | مالک اجزای مدل | RAG، فراخوانی مدل، ارزیابی کیفیت پاسخ | طرح + مجموعهٔ ارزیابی |
| `mobile-app-builder` | مالک اپ موبایل | انتشار اپ، رفتار آفلاین | دیف + چک‌لیست انتشار |
| `rapid-prototyper` | نمونهٔ سریع | اعتبارسنجی ایده، دمو | نمونهٔ قابل اجرا |
| `devops-automator` | مالک CI/CD | خط ساخت، اتوماسیون استقرار | خط لوله + runbook |
| `platform-engineer` | مالک مسیر طلایی | ابزار توسعه‌دهنده، قالب مخزن | قالب + مستند |
| `sre` | مالک قابلیت اطمینان | SLO، هشدار، ظرفیت | SLO + قواعد هشدار |

| `git-workflow-master` | مالک تاریخ گیت | شاخه‌بندی، rebase، کامیت | استراتژی + تاریخ تمیز |
| `technical-writer` | مالک مستند فنی | تغییر رفتار عمومی، راهنمای مهاجرت | مستند |

**قاعدهٔ مالکیت:** `software-architect` حرف آخر را در معماری می‌زند؛
`backend-architect` و `frontend-developer` در دامنهٔ خودشان. اگر دو نفر
مخالف‌اند، تصمیم به `departments/product` یا در صورت لمس مرز اعتماد به
`departments/security` تشدید می‌شود.

## دروازه‌های تحت مالکیت

| دروازه | شرط عبور | شاهد |
| --- | --- | --- |
| G1 طراحی فنی | معماری و قرارداد API مکتوب، جایگزین‌ها رد شده | ADR + طرح API |
| G2 ساخت | کد طبق قرارداد، بازبینی `code-reviewer` انجام شده | دیف + نظر بازبینی |
| G3 اثبات | تست‌های مرتبط سبز، اجرا در محیط واقعی | خروجی تست + لاگ |

## قرارداد ورودی

از `departments/product` فقط این‌ها را می‌پذیریم:

- تسک با معیار پذیرش قابل‌سنجش (قالب: `templates/task-template.md`)
- دامنهٔ صریح: چه چیزی **خارج** از این تسک است
- تصمیم‌های قبلی مرتبط (لینک به `projects/<نام>/decisions/`)

بدون این‌ها تسک برمی‌گردد. نوشتن کد بدون معیار پذیرش، بدهی است نه تحویل.

## قرارداد خروجی

به `departments/security` و `departments/product`:

- دیف قابل بازبینی با پیام کامیت متعارف
- توضیح تصمیم‌های غیربدیهی (چرا این‌طور، نه آن‌طور)
- خروجی واقعی تست‌ها — نه ادعا
- ریسک‌های باز که عمداً پذیرفته شده‌اند، با نام مالک

## ضدالگوها

- ادغام مستقیم به شاخهٔ اصلی بدون بازبینی، به بهانهٔ «تغییر کوچک است».
- «بعداً تست می‌نویسم» — تست بعد از انتشار، تست نیست.
- ساختن انتزاع برای آینده‌ای که در نقشه راه نیست.
- تغییر رفتار API بدون مستندسازی و بدون نسخه‌بندی.
- فراخوانی `incident-response-commander` برای کار روزمره (این نقش برای حادثه است).
