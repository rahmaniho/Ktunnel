# بخش امنیت

مسئول: **از مدل تهدید تا کنترل اثبات‌شده و پاسخ به رخداد.**

## مأموریت

امنیت در این آژانس یک مرحلهٔ پایانی نیست که «اگر وقت شد» انجام شود؛ یک
دروازهٔ G4 است که هر تغییر از آن عبور می‌کند. اما هدف هم «امنیت مطلق» نیست —
هدف **ریسک شناخته‌شده و پذیرفته‌شده** است. ریسک ناشناخته، ریسک مدیریت‌نشده است.

## اعضای تیم و مرز نقش‌ها

| شناسه | نقش در این بخش | وقتی صدایش می‌زنیم | خروجی |
| --- | --- | --- | --- |
| `security-architect` | مالک مدل تهدید و مرز اعتماد | تغییر معماری، سرویس جدید، جریان احراز هویت | مدل تهدید + کنترل‌ها |
| `appsec-engineer` | مالک امنیت کد | هر دیف که ورودی کاربر یا مجوز را لمس می‌کند | یافتهٔ کد + اصلاح |
| `ai-generated-code-auditor` | بازبین کد تولیدشده با مدل | هر دیفی که عمدتاً با AI نوشته شده | گزارش ریسک الگویی |
| `penetration-tester` | اثبات‌کنندهٔ اکسپلویت | قبل از انتشار عمده، پس از تغییر احراز هویت | گزارش نفوذ + بازتولید |
| `cloud-security-architect` | مالک امنیت ابر | IAM، شبکه، ذخیره‌سازی، زیرساخت به‌کد | طرح امنیت ابر |
| `secrets-credential-hygiene-engineer` | مالک عمر رازها | ورود کلید، افشای احتمالی، چرخش | سیاست + سابقهٔ چرخش |
| `compliance-auditor` | مالک انطباق | نیاز به شاهد انطباق، حسابرسی | نگاشت کنترل به شاهد |
| `incident-responder` | پاسخ‌دهندهٔ رخداد امنیتی | نشت داده، دسترسی غیرمجاز، بدافزار | خط زمانی + مهار + درس‌ها |

**تفکیک مهم:** `incident-response-commander` (در بخش نرم‌افزار) فرماندهی
**حادثهٔ عملیاتی** است (سرویس قطع است). `incident-responder` (اینجا) پاسخ به
**رخداد امنیتی** است (داده یا دسترسی در خطر است). اگر معلوم نیست کدام است،
هر دو صدا زده می‌شوند و `security-architect` تشخیص می‌دهد.

## دروازهٔ G4

| شرط | شاهد لازم |
| --- | --- |
| مدل تهدید برای تغییر به‌روز است | سند مدل تهدید با تاریخ |
| ورودی‌های غیرقابل‌اعتماد اعتبارسنجی می‌شوند | اشاره به کد اعتبارسنجی |
| مجوزدهی سمت سرور است، نه فقط در UI | اشاره به چک مجوز |
| رازی در کد، لاگ، یا تاریخ گیت نیست | خروجی اسکن |
| یافته‌های باز با مالک و مهلت ثبت شده‌اند | فهرست یافته‌ها |

بدون این پنج مورد، G4 باز نمی‌شود — حتی اگر `reality-checker` بقیهٔ کار را
تأیید کرده باشد.

## قرارداد ورودی

از `departments/software`:

- دیف قابل بازبینی (نه توضیح شفاهی)
- نقشهٔ جریان داده: چه ورودی، از کجا، به کجا
- تصمیم‌های احراز هویت و مجوز در همان تغییر

## قرارداد خروجی

به `departments/quality` و `departments/product`:

- فهرست یافته با شدت، بازتولید، و پیشنهاد اصلاح
- تصمیم «بازدارندهٔ انتشار» یا «پذیرش با ثبت ریسک»
- برای ریسک پذیرفته‌شده: مالک، مهلت، و شرط بازبینی مجدد

## الگوی کار

```
تغییر ──► security-architect (تغییر معماری؟)
             │
             ▼
      appsec + ai-code-auditor (بازبینی)
             │
             ▼
      secrets hygiene (اسکن) ──► pentest (اگر سطح حملهٔ جدید)
             │
             ▼
        G4: انتشار یا پذیرش ثبت‌شده
```

## ضدالگوها

- «امنیت را بعداً اضافه می‌کنیم» — بعداً یعنی هرگز، یا یعنی رخداد.
- پنهان‌کردن یافته برای اینکه انتشار عقب نیفتد.
- مجوزدهی فقط در رابط کاربری.
- کلید تست داخل مخزن «چون تستی است».
- گزارش نفوذ بدون گام بازتولید.
