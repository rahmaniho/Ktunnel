# جریان کاری: توسعهٔ قابلیت

> **کی اجرا کنیم:** برای هر قابلیت قابل‌استفاده که وارد محصول می‌شود.
> **پیش‌نیاز:** پروژه از جریان [`new-project.md`](new-project.md) رد شده باشد،
> یا قابلیت مستقل از اسپک محصول تعریف شده باشد.

## اصل حاکم

یک قابلیت یک **حلقه** است، نه یک خط. هر بار که کیفیت ایراد می‌گیرد، کار به
مهندسی برمی‌گردد. حداکثر سه چرخه؛ بعد از آن تصمیم اجرایی لازم است.

## گام ۱ — تعریف و برش (نیم روز)

| عامل | کار | خروجی |
| --- | --- | --- |
| `sprint-prioritizer` | جای قابلیت در بک‌لاگ و ظرفیت | تصمیم «حالا / بعداً» |
| `ux-architect` | جریان کاربر و حالت‌های خطا | طرح جریان |
| `product-manager` | معیار پذیرش قابل‌سنجش | معیار پذیرش |

**شرط عبور:** معیار پذیرش وجود دارد و در `projects/<نام>/tasks/` ثبت شده
(قالب: [`templates/task-template.md`](../templates/task-template.md)).
بدون این، گام ۲ شروع نمی‌شود.

## گام ۲ — طراحی فنی (G1)

| عامل | کار | خروجی |
| --- | --- | --- |
| `software-architect` | آیا مرز سرویس یا مدل داده عوض می‌شود؟ | ADR یا «تغییر ساختاری ندارد» |
| `ui-designer` | کامپوننت‌ها و وضعیت‌ها | طراحی آمادهٔ پیاده‌سازی |
| `security-architect` | آیا سطح حمله جدید است؟ | به‌روزرسانی مدل تهدید |

**نکتهٔ برش:** اگر این قابلیت بیش از ۵ کامپوننت یا ۳ سرویس را لمس می‌کند،
به چند قابلیت کوچک‌تر بشکنید. G1 برای هر کدام جداگانه اجرا می‌شود.

## گام ۳ — پیاده‌سازی (G2)

ترتیب پیشنهادی برای بیشتر قابلیت‌ها:

```
backend-architect (قرارداد API)
        │
        ├──► frontend-developer (رابط)
        ├──► mobile-app-builder (در صورت نیاز)
        └──► ai-engineer / data-engineer (در صورت نیاز)
        │
        ▼
git-workflow-master (تاریخ تمیز) ──► code-reviewer
```

قواعد این گام:

- قرارداد API **قبل از** مصرف‌کننده‌اش نوشته می‌شود.
- هر کامیت یک تغییر منطقی؛ پیام متعارف (`feat:`, `fix:`, `refactor:`).
- تست همراه کد است، نه در تسک جداگانه.
- اگر `ai-engineer` درگیر است، مجموعهٔ ارزیابی هم بخشی از تحویل است.

**شرط عبور G2:** بازبینی `code-reviewer` انجام شده، هیچ ایراد مسدودکننده‌ای باز
نیست، و مسیرهای آماده‌شده در گام ۲ پوشش داده شده‌اند.

## گام ۴ — اثبات (G3)

| عامل | چه چیزی را اثبات می‌کند |
| --- | --- |
| `test-automation-engineer` | مسیرهای اصلی و حالت‌های خطا |
| `api-tester` | قرارداد، مرز، و خطاهای API |
| `accessibility-auditor` | دسترس‌پذیری رابط (اگر تغییر UI است) |
| `performance-benchmarker` | نبود رگرسیون در مسیر داغ |

**قاعدهٔ شاهد:** خروجی واقعی اجرا لازم است. «تست‌ها پاس شدند» بدون لاگ،
شاهد نیست. شاهد در `reports/<تاریخ>-<نام-قابلیت>/` ذخیره می‌شود.

## گام ۵ — امنیت (G4)

| عامل | بررسی |
| --- | --- |
| `appsec-engineer` | جریان داده، ورودی، مجوز |
| `ai-generated-code-auditor` | اگر بخش عمدهٔ کد با مدل تولید شده |
| `secrets-credential-hygiene-engineer` | نبود راز در کد/لاگ/تاریخ |
| `penetration-tester` | فقط اگر سطح حملهٔ جدید باشد (یا پیش از انتشار عمده) |

**شرط عبور G4:** پنج شرط `departments/security/README.md` برقرار است، یا
ریسک باز با مالک و مهلت ثبت شده.

## گام ۶ — پذیرش (G5)

| عامل | کار |
| --- | --- |
| `reality-checker` | تطبیق بند‌به‌بند معیار پذیرش با شاهد |
| `technical-writer` | مستند رفتار جدید یا راهنمای مهاجرت (اگر عمومی است) |
| `senior-project-manager` | به‌روزرسانی `STATUS.md` و بستن تسک |

`reality-checker` یکی از سه تصمیم را می‌دهد:

| تصمیم | معنا | قدم بعدی |
| --- | --- | --- |
| **آماده** | همهٔ معیارها با شاهد پوشش داده شد | انتشار |
| **نیاز به کار** | ایراد مشخص و قابل اصلاح | بازگشت به گام ۳ با لیست ایراد |
| **بازدارنده** | مشکل ساختاری در طراحی یا دامنه | بازگشت به گام ۱ یا ۲ |

## جدول چرخهٔ بازخورد

| --- | --- | --- |
