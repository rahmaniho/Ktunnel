# جریان کاری: پروژهٔ جدید

> **کی اجرا کنیم:** وقتی یک پروژه از صفر شروع می‌شود یا یک محصول موجود باید
> بازطراحی ساختاری شود.
> **چه چیزی نمی‌سازد:** کد. خروجی این جریان *تصمیم و نقشه* است، نه پیاده‌سازی.

## پیش‌نیاز

| مورد | چه کسی می‌دهد | باید داشته باشد |
| --- | --- | --- |
| مسئله | کارفرما / صاحب محصول | به زبان کاربر، نه راه‌حل |
| محدودیت | کارفرما | زمان، بودجه، انطباق، فناوری موجود |
| معیار موفقیت | کارفرما + `product-manager` | یک عدد یا شرط قابل مشاهده |

اگر معیار موفقیت وجود ندارد، جریان شروع نمی‌شود. «رضایت کاربر» بدون عدد یا
روش سنجش، معیار نیست.

## گام ۰ — راه‌اندازی پروندهٔ پروژه

```bash
cp -r templates/project-skeleton projects/<نام-پروژه>
# سپس projects/<نام>/STATUS.md را پر کنید
```

مسئول: `senior-project-manager`. خروجی: پوشهٔ پروژه با `STATUS.md` خالیِ آماده.
این گام داوطلبانه است اما اگر انجام نشود، جریان بدون تک‌منبع وضعیت ادامه
می‌یابد و در روز سوم گم می‌شوید.

## گام ۱ — کشف و دامنه (G0)

| ترتیب | عامل | ورودی | خروجی |
| --- | --- | --- | --- |
| ۱ | `business-strategist` | مسئله، بازار، رقبا | تحلیل فرصت + گزینه‌ها |
| ۲ | `ux-researcher` | مسئله، فرض‌ها | ۳ تا ۵ فرض قابل آزمون |
| ۳ | `product-manager` | خروجی ۱ و ۲ | اسپک یک‌صفحه‌ای |

**شرط عبور G0:** اسپک شامل مسئله، کاربر هدف، دامنهٔ «داخل»، دامنهٔ «خارج»، و
معیار موفقیت باشد. دامنهٔ «خارج» اجباری است — بدون آن، پروژه بی‌نهایت می‌شود.

پرامپت نمونه:

```
Activate Product Manager.
مسئله: <...>
محدودیت: <...>
معیار موفقیت: <...>
یک اسپک یک‌صفحه‌ای بنویس با بخش‌های: مسئله، کاربر، دامنهٔ داخل، دامنهٔ خارج،
معیار موفقیت، ریسک‌های اصلی. هیچ راه‌حل فنی پیشنهاد نده.
```

## گام ۲ — طراحی تجربه و معماری (G1)

| ترتیب | عامل | ورودی | خروجی |
| --- | --- | --- | --- |
| ۴ | `ux-architect` | اسپک | جریان اصلی + حالت‌های خطا |
| ۵ | `software-architect` | اسپک + جریان | معماری کلان + ADR |
| ۶ | `security-architect` | معماری | مدل تهدید اولیه |
| ۷ | `sprint-prioritizer` | همهٔ بالا | نقشهٔ راه فازی |

گام ۴ و ۵ می‌توانند موازی شروع شوند اما **نباید موازی تمام شوند**: اگر
معماری جریانی را غیرممکن کرد، جریان بازنگری می‌شود.

**شرط عبور G1:** ADR نوشته شده، مدل تهدید اولیه موجود است، و نقشهٔ راه
حداقل یک فاز «قابل انتشار» دارد (نه فقط فاز ساخت).

## گام ۳ — شکستن به تسک و آماده‌سازی محیط

| ترتیب | عامل | خروجی |
| --- | --- | --- |
| ۸ | `senior-project-manager` | تسک‌های یک‌تا‌سه‌روزه با معیار پذیرش |
| ۹ | `platform-engineer` | قالب مخزن، CI پایه، `CLAUDE.md` پروژه |

**شرط عبور:** هر تسک معیار پذیرش دارد، هر تسک یک مالک دارد، و هیچ تسکی بیش از
سه روز نیست. تسک بزرگ‌تر از سه روز، تسک نیست — فاز است.

## گام ۴ — حلقهٔ بررسی پیش از اجرا

| بررسی | عامل | سؤال |
| --- | --- | --- |
| واقع‌گرایی برنامه | `sprint-prioritizer` | آیا این حجم در این ظرفیت شدنی است؟ |
| ریسک امنیتی | `security-architect` | آیا G4 از ابتدا قابل دستیابی است؟ |
| آمادگی ابزار | `platform-engineer` | آیا محیط برای تسک اول آماده است؟ |

اگر یکی از این سه «نه» بگوید، به گام مربوطه برگردید. شروع ساخت با برنامهٔ
غیرواقعی، بدهی فوری است.

## خروجی نهایی

```
projects/<نام>/
├── STATUS.md            # وضعیت جاری، مالک، گام بعدی
├── SPEC.md              # اسپک تأییدشده (G0)
├── ROADMAP.md           # نقشهٔ راه فازی
├── decisions/           # ADR و تصمیم‌های بازار
├── tasks/               # تسک‌های آمادهٔ اجرا
└── AGENTS-NOTES.md      # تصمیم‌های فرایندی و درس‌های جریان
```

پس از این، جریان [`feature-development.md`](feature-development.md) اجرا می‌شود.
